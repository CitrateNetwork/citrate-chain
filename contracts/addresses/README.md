# Canonical contract-address table

This directory is the **single source of truth** for every Citrate
contract deployed to chain 40204. The federation (citrate-explorer,
citrate-inference-gateway, citrate-node-agent, citrate-sdk-marketplace,
citrate-gui-native, citrate-defense_prime-shell, citrate-buyer-webapp) reads
from a vendored copy of `40204.json` (or imports `@citratelabs/chain-config`,
which embeds it). No consumer hardcodes a contract address.

## Which file is canonical

The live network is **r1007** (chain 40204, block-0 hash
`0xcf68634502b4fca1e977ac8dd35aa006bb40c04208d5cd55f1c2b508bba96631`, live since
2026-11-12T14:00:00Z, public RPC `https://rpc.citrate.ai`).

| File | What it is | Who writes it |
|------|------------|---------------|
| **`40204.json`** | **The canonical book for the live r1007 network.** Consumers read this file. | Generated by [`scripts/addresses/emit_root_book.py`](../../scripts/addresses/emit_root_book.py). Never edit by hand. |
| `r1007/40204.json` | r1007 genesis book: every contract in block 0. r1007 rebuilt r1006's block-0 state with rotated keys; the contracts are CREATE2 deployments the rotation did not move, so the addresses equal r1006's. Input to the root book. | [`scripts/addresses/emit_r1007_books.py`](../../scripts/addresses/emit_r1007_books.py), from the probe. Do not modify. |
| `r1007/40204.postgenesis.json` | r1007 contracts deployed after block 0: the r1007 post-genesis deployer's nonces 0-28 (nonce 4, an AgentDecisionRegistryV2 duplicate, left out), plus `accounts`, the operator EOAs. Input to the root book. | `emit_r1007_books.py`, from the probe. |
| `r1007/40204.provenance.json` | The read-only probe of the live r1007 chain both r1007 books are built from: block-0 hash, a codehash for every contract address, the deployer's nonce, and the AA and TenantHierarchy checks. | Written once from `cast` reads; frozen. |
| `r1006/40204.root.json` | The r1006 root book, archived byte for byte when r1007 went live. | Frozen. |
| `r1006/40204.json`, `r1006/40204.postgenesis.json`, `r1006/address-code.snapshot.json` | The r1006 genesis and post-genesis books and its last getCode snapshot (block 648047). History. citrate-core pinned the r1006 genesis book by sha256. | Frozen. |
| `r1005/` | Archive of the retired r1005 network (genesis state root `0x1dcfc490…`): its book, provenance ledger, DPF harvest and getCode snapshot. History only. | Frozen. |
| `dpf-40204.old.json`, `dpf-40204.pre-2026-07-26.json` | Pre-r1005 DPF harvests. Dead history. | Frozen. |
| `schema.json` | JSON schema for the book shape (root, r1007, r1006 and r1005 books). | By hand. |
| `GENESIS_ALLOC_TEMPLATE.json`, `I64S1_PROJECTION.md` | Ceremony inputs and planning notes. Not address books. | By hand. |

The root book's `source` field names both r1007 books with the sha256 of the
file each was generated from, so a reader can confirm which inputs produced it.
`verification/tests/test_root_book.py` and `test_r1007_books.py` (claims-truth
CI) fail when a committed book differs from its generator's output.

`accounts` (top level of the root book, from the post-genesis book) names operator
EOAs consumers need, for example the bundler signer and the faucet. They have no code
and are not contracts; `@citratelabs/chain-config` exports them as `accounts`, and
`getAddress` does not resolve them.

## How consumers use it

Each consumer ships a small script (`scripts/sync-addresses.{sh,mjs}` or
similar) that:

1. Reads `../../citrate-chain/contracts/addresses/40204.json` (the
   sibling-repo path under `Citrate-Labs/`), or imports
   `@citratelabs/chain-config`.
2. Optionally narrows the read to the contracts the consumer uses.
3. Writes a vendored copy at a path the consumer's build system picks
   up, typically `src/generated/addresses.json` for TS and
   `crates/<crate>/src/generated/addresses.json` for Rust.

The vendored copies are **committed** and imported at build time, so the
dev-time sync is the only moving piece. Before trusting any address, a consumer
should compare the book's `genesisHash` with `eth_getBlockByNumber(0x0).hash`
on the chain it talks to.

## Schema (`40204.json`)

| Field | What |
|-------|------|
| `chainId` | 40204 (always: this is the chain-40204 table) |
| `chainName` | Human label |
| `rpcUrl` | Canonical public RPC the apps default to |
| `explorerUrl` | Public CitrateScan URL |
| `genesisHash` | Block-0 hash of the network this book describes |
| `deployer` | EOA of the genesis ceremony |
| `deployedAt` | Genesis timestamp (r1006 block 0: 2026-01-01T00:00:00Z) |
| `regenerator` | The script that writes this file |
| `source` | The two r1006 books (path, sha256, deployer, deployedAt, contract count) |
| `contracts` | Name → address for every deployed contract: the genesis contracts, then the post-genesis contracts under their own keys (for example `Quorum.AnchorRegistry`) |
| `aaStack` | ERC-4337 v0.7 stack (EntryPoint, wallet, factory, paymaster, validators, guardian module) |
| `genesis` | Genesis predeploys: the Arachnid CREATE2 deployer, the P-256 verifier, OrangeSeed (proxy) and OrangeSeedV0 (implementation) |
| `precompiles` | Built-in addresses the executor binds. Not contracts: `eth_getCode` returns `0x` by design |
| `CitrateMemberSBT`, `MembershipStakeVault` | Top-level pins of the same-named `contracts` entries |
| `governance` | `GOVERNANCE` and `GUARDIAN`, the same addresses as `contracts.GovernanceTimelock` and `contracts.GuardianTimelock` |

r1006 books spell addresses in lowercase (r1005 used EIP-55 checksums); compare
addresses case-insensitively. A key may contain a dot (`Quorum.AnchorRegistry`):
read it as one key (`.contracts["Quorum.AnchorRegistry"]` in jq,
`.contracts['Quorum.AnchorRegistry']` in Forge JSONPath), never as a nested path.

On r1006, GOVERNANCE and GUARDIAN are OpenZeppelin `TimelockController`s
(`getMinDelay()` is 172800 s and 3600 s) whose proposer, executor and canceller
is a `MultisigProposer` (`GovernanceMultisig` 3-of-5, `GuardianMultisig` 2-of-3),
with the `GuardianCanceller` veto on GOVERNANCE. The book does not repeat those
parameters; read them from the chain.

## Regeneration

```bash
python3 scripts/addresses/emit_r1007_books.py        # write the r1007 books from the committed probe
python3 scripts/addresses/emit_root_book.py          # write 40204.json from the r1007 books
python3 scripts/addresses/emit_root_book.py --check  # exit 1 if the committed root is stale
node packages/chain-config/scripts/generate.mjs      # refresh the package snapshot
python3 verification/check_address_code.py --probe   # live eth_getCode snapshot (read-only)
```

The generator fails closed when the inputs disagree (chain id, metadata,
malformed addresses, a post-genesis key that redefines a genesis key, an address
under two names, unknown top-level keys).

## Adding a contract deployed after block 0

1. Deploy it; keep the canonical receipt.
2. Add it to `r1007/40204.postgenesis.json` under a key that does not shadow any
   genesis name (the root-book generator refuses a shadowing key). Today that book is
   generated from the probe, so extend the probe record and `emit_r1007_books.py`
   with the new receipt rather than editing the book.
3. Regenerate the root book and the chain-config snapshot, re-probe the getCode
   snapshot, and update `verification/claims.json` `deployed_contracts`.
4. For each consumer that needs the new address, rerun its `sync-addresses`
   script and open one PR per consumer.

Never edit the r1007 or archived books and never edit the root book in place.

## r1005 archive

`r1005/` keeps the retired r1005 network's records as they were when r1005 was
live. Paths inside them point at the archive.

### Fresh-keys reroll: the r1005 book came from the chain, not broadcasts

The r1005 book (`r1005/40204.json`) was **not** produced by
`scripts/ops/emit-address-table.sh`. Its broadcast inputs were unreliable: some
scripts were run more than once (a failed tunnel batch followed by a successful
on-box batch), some `run-latest.json` files were overwritten by an rsync, and the
emitter falls back to stale addresses when a broadcast is missing. Simulating the
deploy scripts doesn't work either: the governance / DPF / cit_agent / Quorum
scripts use plain `new` (nonce-based CREATE), so a simulation prints
*next-nonce* addresses that have no code.

Instead, the book was derived from the chain itself.
`r1005/40204.provenance.json` records every transaction the deployer
(`0x7DAbC319…Acdf`, r1005 reroll 2026-10-06, genesis state root `1dcfc490…`) sent
on that chain: nonces 0–102, contiguous, all with `status=1`. For each transaction
it records the tx hash, block, the created address, and the forge artifact whose
creation code prefixes the init code, and marks each entry `canonical` or
`orphan` (the leftover of a partial first run that a complete rerun superseded).
Where one contract type had several live instances, the book prefixed the key
with its role (`AnchorRegistry`, `QuorumAnchorRegistry`,
`CitAgentAnchorRegistry`; the cit_agent 2-of-3 timelock `CitAgentTimelock`).

### HUP registry set (HUP-S7.1, r1005)

On r1005, `OrganizationSBT`, `AgentSBT`, `CapsuleRegistry`, `AnchorRegistry`,
`BenchmarkRegistry` and `SkillRegistry` were deployed by
`script/DeployHupRegistries.s.sol` after the main ceremony and merged into the
book by `scripts/ops/hup-book-update.py`, with `scripts/ops/hup-provenance-update.py`
appending the same broadcast to the ledger. Procedure:
[`docs/ops/HUP_REGISTRY_REDEPLOY_RUNBOOK.md`](../../docs/ops/HUP_REGISTRY_REDEPLOY_RUNBOOK.md).
Those tools now default to the r1005 archive. On r1006 the HUP registries are
genesis contracts.

### Broadcast-era emitter

`scripts/ops/emit-address-table.sh` builds a book from
`broadcast/Deploy*.s.sol/40204/run-latest.json` and `.env.testnet`. It predates
r1005 and still writes `contracts/addresses/40204.json` by default (the genesis
ceremony scripts use that path as their working output). Do not commit its
output over the generated root book.

## Out-of-scope (intentionally)

- **Multi-chain tables.** When Citrate ships a second chain (testnet,
  mainnet split), add `40205.json` alongside `40204.json`. Consumers
  pick by chain id at boot.
- **Versioned upgrades.** If a contract is upgraded (new address for
  the same name), bump the key (e.g., `IPFSIncentivesV2`) rather than
  silently rotating, so consumers fail loudly on a missing name.
- **Off-chain endpoints.** This file is contracts-only. RPC URLs,
  bundler URLs and identity URLs live in `.env.testnet` /
  `.env.production` per app.
